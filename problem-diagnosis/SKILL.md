# 问题诊断

先判断"该不该解、解什么"，再判断"怎么解"。顺序不能反。

## 第一步：判断问题类型

- **故障类**（报错、崩溃、数据不对、性能劣化）→ 直接做根因定位
- **需求类**（"帮我优化 X""加个功能""改进一下"）→ 先重述问题，再定位根因

判据：故障类有客观错误现象，需求类只有主观期望。

## 第二步：质疑问题定义（仅需求类）

分开写两件事：

1. 用户真正想达成的**目标**
2. 用户描述的**手段**

逐条检查三种误判：

| 误判 | 判据 | 处理 |
|---|---|---|
| 把症状当原因 | 描述的是现象（"很慢"）还是成因（"N+1 查询"） | 追问现象背后的成因 |
| 把手段当目标 | 说的是"怎么做"（"加缓存"）还是"要什么"（"响应 <200ms"） | 拆掉手段，只留目标 |
| 方案写进需求 | 需求里已经锁定某个具体实现 | 指出锁死了解空间，给替代方案 |

如果存在更值得解决的问题，直接说出来，并说明：为什么更值得解、需要什么、不解决会怎样。

给出 2–3 个「问题重述」版本，标注各自的解决成本和收益差异。

**如果判断原定义没问题，也要说明为什么。不要为了反对而反对。**

## 第三步：第一性原理归因

1. 列出所有可能成因，按证据强度标注：`[确证]`（代码/日志/文档直接支撑）、`[推测]`（间接线索）、`[无证据]`（纯直觉）
2. 明确区分**症状**和**根因**
3. 用 5 Whys 追到不能再追，输出根因链：`现象 → A → B → 根因`
4. 判断每段成因的性质：

| 性质 | 含义 |
|---|---|
| 有意设计 | 当前仍然需要 |
| 历史遗留 | 当时需要，现在不需要 |
| 约束已消失 | 为已不存在的问题引入 |

## 第四步：给出修复方案

修复必须针对根因。**禁止打补丁**：

- 不许只加 `if` 判断绕过
- 不许只包 `try-catch` 吞掉
- 不许只加 `sleep` / `retry`
- 不许只调大超时时间
- 不许只升级依赖版本碰运气

## 输出格式

```
【问题重述】（仅需求类）
目标：<用户真正想要的>
手段：<用户描述的做法>
误判：<有/无，具体是哪种>
更值得解的问题：<有/无>

【根因链】
现象 → A → B → 根因
证据强度：[确证/推测/无证据]
性质：有意设计 / 历史遗留 / 约束已消失

【修复方案】
最小可执行改动：<具体到文件和函数>
验证方式：<如何证明根因被消除，而不是症状被掩盖>
回滚方式：<如何撤回>

【风险】
影响范围 / 不可逆的部分
```

## 硬约束

1. **先给根因假设，验证通过后再动手改代码。**
2. 每条结论必须标证据强度，禁止把推测说成事实。
3. 验证方式必须能区分"根因被消除"和"症状被掩盖"——只测"现在不报错了"不算验证。
4. 需求类问题必须先重述再归因。代码改到一半才被推翻，是最大的浪费。
5. 时间盒：单次分析限定在当前任务涉及的模块；需要扩大范围先说明理由和预估成本。
6. 中文回答，结论先行，分点罗列，关键结论加粗。
