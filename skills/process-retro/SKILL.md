# 流程复盘

两个子任务数据源不同，可以并行。

## 子任务 A：PR 流程瓶颈

### A.1 明确数据源

- 时间窗：`<XX>` 天（必须是具体数字，不要留占位符）
- 数据字段：PR 列表、创建→合并耗时、评审等待时长、CI 时长、状态

### A.2 给分布，不只给排名

- P50 / P90 / 最大值
- 各阶段耗时占比：等待评审 / CI / 修改往返

只给排名会误导——最慢的那个可能是偶发。

### A.3 归因到具体阶段

找出最慢的 5 个，逐个拆到具体阶段。**禁止笼统说"流程慢"。**

### A.4 区分异常值与系统性问题

| 类型 | 特征 | 处理 |
|---|---|---|
| 异常值 | 只出现一次，有特殊原因（大改、跨团队、长假） | 记录，不投入 |
| 系统性问题 | 反复出现，多个 PR 共享同一模式 | 优先治理 |

### A.5 每个瓶颈给出四项

- 优化动作
- 预期收益（能省多少时间）
- 实施成本
- 是否值得做（收益 ÷ 成本）

标注哪些数据是实测、哪些是估算。

## 子任务 B：Bug 复盘与沉淀

### B.1 明确范围

- 时间窗：`<XX>`
- 记录数：`<N>` 条
- 数据源：issue / PR / 回滚记录 / 线上事故

### B.2 根因聚类（不要只统计数量）

对每条做根因归类，再聚类成共性根因。每类标注：出现次数、影响面、涉及模块。

### B.3 区分「人的问题」和「系统的问题」

| 类型 | 表现 | 能否自动化 |
|---|---|---|
| 人的问题 | 不知道、忘了、疏忽 | 不能 |
| 系统的问题 | 没有工具拦住、没有检查、没有约束 | 能 |

**只有系统能被自动化。** 把人的问题写成规则，等于要求大家"更小心"，无效。

### B.4 沉淀物必须可执行

三选一或多选：

| 类型 | 要求 |
|---|---|
| 项目规则 | 写进 CONTRIBUTING / 检查清单，**必须具体到可判定** |
| 自动化 | CI 检查 / lint 规则 / 脚本，**必须给出可运行的代码** |
| Skill | **必须给出触发条件和执行步骤** |

**禁止**输出"加强 code review""提高意识""注意边界情况"这类无法执行的建议。

### B.5 每项沉淀物标注

- 拦截哪类问题
- 预期减少多少返工
- 实施成本
- 如何验证它真的生效（不是"上线了"就算生效）

### B.6 给优先级

明确说：先做哪 2 项，为什么。

## 输出格式

```
【A. PR 流程】
时间窗：<XX> 天｜样本：<N> 个 PR
分布：P50 <a> / P90 <b> / 最大 <c>
阶段占比：评审等待 <>% / CI <>% / 往返 <>%

| # | PR | 最慢阶段 | 归因 | 类型（异常/系统） | 优化动作 | 收益 | 成本 | 值得做 |
|---|---|---|---|---|---|---|---|---|

【B. Bug 复盘】
时间窗：<XX>｜样本：<N> 条

| # | 共性根因 | 次数 | 影响面 | 涉及模块 | 人的问题/系统的问题 |
|---|---|---|---|---|---|

【沉淀物】
| # | 类型 | 内容 | 拦截哪类问题 | 预期减少返工 | 成本 | 如何验证生效 |
|---|---|---|---|---|---|---|

【优先级】
先做：<2 项>，理由：...
```

## 硬约束

1. **XX 必须替换成具体数字**。留占位符等于让模型猜一个数然后假装分析过。
2. 给分布不只给排名。
3. 归因到具体阶段，禁止"流程慢"这种笼统结论。
4. 区分人的问题和系统的问题——只有后者能沉淀。
5. 沉淀物必须可执行，禁止正确的废话。
6. 每项沉淀物必须说明如何验证它真的生效。
7. 数据要标注实测 / 估算。
8. 中文回答，结论先行，分点罗列，关键结论加粗。
