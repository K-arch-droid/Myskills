# 存量代码审计

**顺序：先做新人视角审计，再做 Git 考古。** 反过来会陷进历史细节里，被旧上下文带偏。

## 第一步：新人认知成本审计

模拟一个能力很强但完全不了解项目的工程师接手第一天。

### 1.1 给出最小上手路径

- 需要读哪些文件
- 按什么顺序读
- 哪些地方会卡住、为什么

### 1.2 定位认知成本高点（四类）

| 类别 | 判据 |
|---|---|
| 命名混乱 | 名字和实际行为不符（`getUser` 里写了数据、`Manager` 其实只是个 DTO） |
| 抽象过度 | 只有一处实现却做了接口 / 工厂 / 泛型 / 策略模式 |
| 职责不清 | 一个文件干三件事，或一件事散在五个文件 |
| 隐式上下文 | 必须先知道某个背景（某次事故、某个客户、某个已下线服务）才能看懂 |

### 1.3 硬约束

- **每条结论必须落到「具体文件 + 行号 + 具体问题」**
- 禁止输出"命名不规范""抽象过度""职责不清晰"这类万金油结论——这类话对任何代码库都成立，等于没说
- 每条给出具体简化动作：改名成什么 / 合并到哪 / 拆成什么 / 删掉哪个抽象

### 1.4 排序

按 `认知成本 ÷ 改动成本` 排序，**只推荐前 3 项**，其余列为备选并说明为什么可以放后面。

## 第二步：Git 考古

### 2.1 限定范围（必须显式声明）

- 模块 / 目录：`<范围>`
- 时间窗：`<X 个月>`
- 最多分析：`<N>` 个关键 commit / PR

超限先给阶段性结论，不要硬撑。

### 2.2 三分类 + 证据强度

| 类别 | 含义 | 处理 |
|---|---|---|
| 有意设计 | 当前仍然需要 | 保留，补文档说明原因 |
| 历史遗留 | 当时需要，现在不需要 | 可移除 |
| 约束已消失 | 为已不存在的问题引入 | 优先移除 |

证据强度必须标注：

- `[确证]` commit message / PR 描述 / 代码注释明确写了原因
- `[推测]` 从时间线和上下文推断
- `[无证据]` 查不到任何说明

### 2.3 重点找「约束已消失」

特征：当时为解决某个问题引入，但那个问题现在已不存在。

常见信号：

- 依赖升级后 workaround 不再需要
- 流量量级变了，保护性限流成了瓶颈
- 某个服务下线了，兼容代码还在
- 某个客户不做了，特判分支还在

### 2.4 输出可安全移除清单

| 项 | 内容 |
|---|---|
| 移除范围 | 具体文件 / 函数 / 配置 |
| 移除理由 | 属于哪一类 + 证据 |
| 验证方式 | 怎么证明移除后没问题 |
| 回滚方式 | 怎么撤回 |
| 风险等级 | 高 / 中 / 低 |

### 2.5 硬约束

**禁止把「古老的代码」直接判定为「历史包袱」。** 老代码可能是被线上验证过的关键设计，只是没人记得为什么这么写。

## 输出格式

```
【最小上手路径】
1. 读 <文件> — 作用
2. 读 <文件> — 作用
卡点：<哪里会卡，为什么>

【认知成本清单】
| # | 类别 | 位置（文件:行） | 具体问题 | 简化动作 | 成本÷收益排序 |
|---|---|---|---|---|---|
推荐做：<前 3 项>
备选：<其余，为什么可以放后面>

【Git 考古】
| 设计 | 分类 | 证据强度 | 证据（commit/PR） | 处理建议 |
|---|---|---|---|---|

【可安全移除清单】
| # | 范围 | 理由 | 验证 | 回滚 | 风险 |
|---|---|---|---|---|---|
```

## 硬约束

1. 先审计（第一步）再考古（第二步）。
2. 认知成本结论必须落到文件+行号，禁止万金油。
3. Git 考古必须标证据强度，禁止把推测说成事实。
4. 老代码不等于包袱。
5. 移除建议必须带验证方式和回滚方式，缺一不许输出。
6. 范围必须显式限定，否则会烧掉大量上下文。
7. 中文回答，结论先行，分点罗列，关键结论加粗。
