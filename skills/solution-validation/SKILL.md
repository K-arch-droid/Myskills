# 方案验证

先证伪，再推演。**方案本身是错的，推演它的二阶影响纯属浪费。**

## 第一步：红队证伪

### 1.1 明确攻击目标

- 要推翻的方案（具体到关键决策点）
- 它成立的核心假设（必须具体到可被检验）

| 坏假设（不可检验） | 好假设（可检验） |
|---|---|
| 系统应该是稳定的 | QPS 峰值不超过 1000 |
| 用户不会这么操作 | 单用户日请求 < 100 |
| 依赖方不会挂 | 依赖 P99 可用性 99.9% |

### 1.2 逐条攻击，覆盖六类边界

| 类别 | 攻击点 |
|---|---|
| 空值与边界 | null、空集合、零长度、负数、超大值 |
| 并发 | 竞态、重复提交、锁粒度、死锁 |
| 超时与重试 | 超时后重试是否幂等、雪崩 |
| 量级变化 | 流量翻 10 倍、数据量翻 100 倍 |
| 依赖故障 | 下游挂掉、第三方限流、网络分区 |
| 时间 | 时区、夏令时、跨天、跨月 |

### 1.3 每条攻击标注两个维度

- 能否被现有证据推翻：`[能]` / `[不能]` / `[不确定]`
- 致命程度：`[致命]` / `[严重]` / `[可接受]`

### 1.4 只保留致命和严重

可接受的直接说明为什么可以接受，不要堆砌。用数量制造严谨感等于没有重点。

## 第二步：重新评估

- 给出修正后的方案，**或**明确说"原方案成立，因为 X"
- 如果推翻了原方案，**必须给出替代方案**。不能只破坏不建设。

## 第三步：二阶 / 三阶影响推演

分四条线，每条都要写清「触发条件」和「影响量级」：

| 线 | 推演内容 |
|---|---|
| 模块耦合 | 谁依赖它、改动传播到哪、有没有隐式契约 |
| 用户行为 | 会不会被绕过、被滥用、被误用、形成依赖 |
| 系统复杂度 | 新增几个概念、几条隐式约束、几处需要记住的例外 |
| 长期维护 | 新人理解成本、后续改动的传播范围、排障难度 |

**禁止**只说"可能会变复杂"。必须写清量级（如"新增 2 个概念，改动会波及 3 个模块"）。

标注**可逆性**：可逆的影响可以接受，不可逆的必须优先处理。

## 第四步：取舍

只列值得处理的影响，按量级排序，**最多 5 条**。其余归入「可接受，无需处理」并说明理由。

对排名前 2 的影响，给出预防措施，以及**预防措施本身的成本**——如果预防成本高于影响本身，就不该做。

## 输出格式

```
【攻击目标】
方案：<关键决策点>
核心假设：<可检验的假设>

【攻击清单】
| # | 攻击点 | 能否推翻 | 致命程度 | 应对 |
|---|---|---|---|---|

【重新评估】
结论：<原方案成立 / 需修正为 X>
理由：...

【影响推演】
| 阶 | 线 | 触发条件 | 影响量级 | 可逆性 |
|---|---|---|---|---|

【取舍】
优先处理（前 2）：...
可接受（其余）：... 理由：...
```

## 硬约束

1. **先证伪，后推演**。方案本身不成立时，不做影响推演。
2. 假设必须可检验。"系统应该没问题"不是假设，是侥幸。
3. 攻击清单只留致命和严重，不要用数量制造严谨感。
4. 影响必须带触发条件和量级，禁止"可能""也许"。
5. 不可逆影响优先于可逆影响，无论量级大小。
6. 推翻方案必须给替代方案。
7. 中文回答，结论先行，分点罗列，关键结论加粗。
