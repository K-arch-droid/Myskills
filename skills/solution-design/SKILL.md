# 方案设计

先澄清，再发散，最后收敛到推荐。

## 第一步：澄清（最多 3 问）

只问「答案会改变方案」的问题。

每个问题必须包含：2–4 个选项，并标明默认值。

不影响方案的细节自己用默认值，不要问。先写出你的默认假设，让用户可以只纠正偏差，而不是从头描述。

**禁止**：

- 问"你想要什么样的"（无选项）
- 问"还有什么要求吗"（无信息量）
- 一次问超过 3 个

## 第二步：跨领域类比找方案

### 2.1 把问题抽象成结构，而不是领域

| 结构类型 | 典型场景 |
|---|---|
| 流量调度 | 限流、排队、削峰 |
| 一致性权衡 | 缓存失效、跨服务事务 |
| 故障隔离 | 熔断、舱壁、降级 |
| 资源竞争 | 锁、连接池、配额 |
| 复杂度治理 | 分层、边界、契约 |

### 2.2 给出 3 个以上不同领域的解法

每个必须写明：

- **具体来源**：公司 / 项目 / 论文 / 系统名（必须可核查）
- **核心机制**
- **它成立的隐含前提**

### 2.3 检验前提

明确说明这些前提在当前场景成立吗。不成立的直接排除，不要硬套。

类比只提供思路，落地方案必须重新设计。

**禁止**："某领域有一种方法""业界通常……"这类无法核查的表述。给不出可核查来源就标 `[无证据]`。

## 第三步：出 3 版方案

3 版必须真的不同——不是同一方案的三种措辞。

判断标准：**任意两版在核心权衡上必须不同**（一致性 vs 可用性、性能 vs 可维护性、自研 vs 引入依赖、强一致 vs 最终一致）。

每版标注：

| 项 | 内容 |
|---|---|
| 核心思路 | 一句话说清 |
| 适用场景 | 什么情况下选它 |
| 代价 | 要付出什么 |
| 风险 | 什么情况下会出事 |
| 什么时候不该选 | 明确的排除条件 |

## 第四步：给推荐排序

明确说：推荐哪版、为什么、什么情况下改选其他版。

**不要让用户自己从零比较。**

## 输出格式

```
【默认假设】
1. ...
2. ...

【待确认】（最多 3 个）
Q1. <问题>（默认：A）
   A. ...  B. ...  C. ...

【跨领域参考】
| 来源 | 核心机制 | 隐含前提 | 本场景是否成立 |
|---|---|---|---|

【方案 A】核心思路 / 适用 / 代价 / 风险 / 排除条件
【方案 B】...
【方案 C】...

【推荐】
排序：X > Y > Z
理由：...
改选条件：...
```

## 硬约束

1. **澄清在出方案之前**。先出 3 版再问偏好，等于让用户在错误的方向上做选择。
2. **跨域类比必须给可核查来源**。给不出就标 `[无证据]`。
3. 3 版方案必须在核心权衡上不同。
4. 如果用户的要求里有互相冲突的地方，直接指出冲突并给取舍建议，**不要试图全都满足**。
5. 中文回答，结论先行，分点罗列，关键结论加粗。
